Asynchronous Agentic Memory for Long Video Generation

NVIDIA·MIT·CUHK

TL;DR

  • Real-time video generators stream minutes of video with a new prompt for every shot, but they forget, so a face, a jacket or a kitchen you come back to has changed a few shots later. Agentic LongLive adds a memory agent that remembers them.
  • Existing video agents work only offline: they read the whole script in advance and plan each shot while the generator waits. We run ours next to the generator instead of in front of it, on its own GPUs, where it keeps images of the people, objects and places and passes them to the generator, so the video never waits for memory.
  • With the agent running, FastH3-Omni, LongLive-H3 and LongLive-2.0 all stay real time on B200s, at 29.0, 34.7 and 34.3 FPS for 24 FPS video.
  • Compared with LongLive-2.0, characters, story details and revisited places stay consistent, with gains of 26 to 45 points, and identity still holds after 14 minutes. Watch the long stories ↓
  • The same agent also gives robot video models a memory, so a tube shut in a drawer or a fan the robot turned away from is still the same when it comes back. Watch the robot videos ↓

How fast is that in frames per second? With the agent running, FastH3-Omni, LongLive-H3 and LongLive-2.0 all stay above 24 FPS, and Agentic LongLive (Offline) does not. The gray bars are the generators alone. LongLive-2.0 runs as fast with the agent as without it (34.3 and 34.1 FPS), because the agent has GPUs of its own. LongLive-H3 and FastH3-Omni lose about 4 FPS and stay 5 to 11 FPS above real time. H3 models put the prompt first in their input, so the memory pictures can only go in after the prompt arrives, on the generator’s own GPUs (about 0.5 s per shot on LongLive-H3). Long streams

Forgetting adds up over a long stream. We extended nine hand-written stories to 80 shots, about 14 minutes each, and ran them on LongLive-2.0 with two seeds, once with our memory and once with its built-in memory. With our memory, the protagonist stays recognizable for all 14 minutes. Identity stays near 90%, while the built-in memory drops from 65% to about 30% after two minutes. Image quality behaves the same way. Ours stays flat, and the built-in memory decays over the whole story. The switch above the chart shows both.

1The System

Agentic LongLive pairs a real-time video generator with a memory agent that runs next to it on separate GPUs. The generator keeps streaming, and the agent keeps a memory of the story and hands it over before each shot. Here is how the pieces fit together.

1.1Memory is built while the video plays

In a live stream, nobody knows the next prompt in advance. It arrives only when its shot starts. Drawing and checking a memory image takes seconds, so an agent that worked between shots would freeze the video every time a prompt came in.

So the agent runs in parallel, on its own GPUs, one shot ahead of the generator. While shot i−1 plays, it reads the prompts revealed so far and prepares the memory for shot i. The first version is committed as soon as it is drawn, and a redraw replaces it only if it passes a check. At the boundary, the generator simply takes the newest version that is ready.

The agent reads prompts and never the generated video. A mistake in one shot is therefore never written back into memory, and it cannot spread to the next shot.

1.2Two layers of memory

A real-time generator has no notebook. Everything it remembers lives in its attention. An autoregressive model like LongLive keeps the key/value (KV) cache of its last few chunks, plus a few sink slots at the very start that are never dropped. Both are filled with the model’s own output. The sink keeps the opening frames and the window keeps the last few seconds. Everything in between, such as the jacket from shot 3 or the kitchen from shot 5, is lost, and a small mistake in the last shot becomes part of what the model remembers.

That raises a simple question. Could the agent maintain this sink and KV cache for the generator, or even generate them? The agent reads every prompt, never drops an entity and has time to check its work. It needs two things for this: a memory of the story that it updates as prompts arrive, and a way to write that memory in a form the video model can read. These are the two layers.

Take a short story from the paper. Leo and his bichon Mochi have a picnic in the park, get caught in a sudden rain, change into rain gear at home, and go for a walk down a rainy street. What should the agent remember?

The first layer is an entity memory. Every person, object and place gets a short text state and an image, and both change only when a prompt changes them. When the rain comes, Leo, Mochi and the blanket each get a new, wet version. At home, Leo puts on a rain jacket and Mochi a yellow raincoat. The images keep what should last, such as identity, clothing and wetness, and leave pose and action to the next prompt.

The second layer turns these entities into pictures the video model can read. A sink is made of frames, so whatever the agent wants remembered has to look like a frame. A global image G shows the main characters and key objects as they are now. A shot memory image M shows the current place with the entities that are active there. Both are composed from the entity images instead of being redrawn from text, so Mochi keeps the same face from shot to shot.

1.3Memory enters through the attention sink

Now the agent has pictures, and the generator already has a place it never forgets. The video model generates the video chunk by chunk, and each new chunk looks back at a short window of earlier ones. The first slots of that window, the attention sink, are always kept. G and M are encoded by the VAE and prefilled as key/value blocks into exactly these slots before the shot that uses them. Without the agent, the sink keeps the first frames of the video. Now it keeps what the agent chose to remember.

A shot starts from G and the two latest memory images, followed by a short gap as at a scene cut. Once its first chunk is generated, that chunk is pinned in place of the memory images, next to G, and the window rolls on as new chunks push old ones out. Memory sets the look at the start of a shot and then steps aside, so the video follows the prompt instead of copying the layout of the memory image.

Few-step generators that make a whole shot at once, such as FastH3-Omni, need no sink of chunks. The memory images are placed just before the shot on the model’s time axis, like frames of an earlier shot followed by a cut, and the shot is generated after them. The memory and the agent are the same.

When the next prompt arrives, the agent decides where the story is. The same place keeps the memory. An earlier place recalls the newest image drawn there. A new place keeps only G. This short choice is the only model call on the critical path.

1.4Learning what to remember

The memory images have only a few slots, and the agent has to fill them before it knows the next prompt. Should it draw Leo’s umbrella now, or the street? A small planner, Qwen3-8B with LoRA, learns this with reinforcement learning. For every shot it writes one JSON update from the prompts revealed so far.

After shot 8 of the Leo story, for example, it notes that Leo is in rain gear and the umbrella is wet. It puts Leo, Mochi and the umbrella into G, and the street, Leo and Mochi into M. A hindsight reward then scores this update against annotations of later shots. Those shots stay hidden from the policy and are used only for scoring.

A text judge checks the states that later shots need. An image judge renders G and M and checks that the next shot’s entities are recognizable. The image weights come from real video outcomes: an entity gains about as much from being in G as from being in M, and each M member that never appears costs a little. GRPO updates the policy, while the image, video and judge models stay frozen.

2.1Long stories

The buttons switch between three systems, all built on MiniMax-H3. Agentic LongLive (FastH3-Omni) runs our system with FastH3-Omni, a few-step distillation of MiniMax-H3 released by FastVideo that generates each 8 s shot at once. Agentic LongLive (AR) runs it with LongLive-H3, which is autoregressive and streams the shot chunk by chunk, so its first frames appear 1.5 s after the prompt. Both run in real time with the same memory agent.

Agentic LongLive (Offline) shows how far the same idea goes without a time limit. Its agent runs on commercial APIs: Gemini 3.8 Flash plans the memory, checks every image and rewrites each prompt into H3’s reference format, and an image model draws the entity images (Gemini 3 Pro Image for these stories, GPT Image 2.5 in the paper). The generator is the original 50-step MiniMax-H3 Ref2VA, which takes up to six of these images as references for each shot. It is not real time. One 8 s shot takes about 556 s of generation on four H100s. A memory update takes one to two minutes of API time, so it is ready before the shot that uses it, and only the 25 s prompt rewrite waits for the new prompt. Because nothing here runs live, these videos have no agent view.

For each story and system we ran only four seeds and picked one of them for this demo, except Spare Parts, which is hard for the base model and got more seeds on Agentic LongLive (AR).

2.2Robotics

Every robot video in this section is generated by a robot video model. It is a video-generation simulation, not footage of a real robot.

Robot video models are used to simulate what a robot will see. A robot keeps turning away from things and shutting them inside drawers, and later it comes back for them. A robot video model that continues each instruction from its last frame has nothing left of what went out of view, so it makes something new up. Long-WAM, our companion work in the LongLive family, scales how much visual history a world-action model can use while staying real time. Our agent complements it by remembering what has already left that history, and the paper also tests our memory on Long-WAM’s robot video model. A robot works in one continuous scene, not a sequence of separate shots, so the agent has to watch the generated video itself to know what to remember. It writes down where each object is and what it looks like, and keeps pictures of the scene, of the inside of open containers and close-ups of objects. When an instruction brings something back, it hands the right pictures to the generator. While a segment is being generated, it watches the last finished one and prepares the next, so its time stays hidden inside generation. For this, each instruction is given one segment in advance. After the robot turns away and comes back, the green tube is still in the drawer and the square desk fan is still the same fan.

Each example is one 64 s video generated from a single input image (from RoVid-X) and eight robot instructions of 8 s each, with no cuts. Left: the video model alone, FastH3-Omni (8 steps), with the same instructions. Right: Agentic LongLive (FastH3-Omni), the same model with our agent (Qwen3.6-35B-A3B), which passes it up to two memory pictures. Because the agent works while the video is generated, its notes trail the video by one instruction. Green parts of the timeline are where something should come back. Across 30 such videos, a blind judge finds the returning thing unchanged and in the same place at 56% of these moments with our agent and at 20% without it.
